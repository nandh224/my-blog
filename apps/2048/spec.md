# 2048 게임 - 계획 문서 (Plan)

> 이 문서는 계획 단계 산출물이다. 실제 게임 코드(HTML/CSS/JS)는 포함하지 않으며,
> Embed/Build 단계에서 이 계획을 바탕으로 구현한다.

## 1. 개요

`my-blog` 저장소는 마크다운 블로그 외에 미니 웹앱들을 `/apps/` 아래에 포트폴리오 형태로
호스팅할 예정이다. 이번 앱은 방향키(및 모바일 터치 스와이프)로 조작하는 **2048 퍼즐 게임**이다.

- 4x4 그리드에서 같은 숫자 타일을 밀어 합쳐 2048 타일을 만드는 게임
- 현재 점수 + 최고 점수(localStorage 저장) 표시
- 프레임워크 없이 순수 HTML/CSS/JS로 구현 (블로그 본체와 동일한 기술 스택 제약)
- 블로그 본문과 달리 앱은 자체 완결적(self-contained)이며, 블로그의 `styles.css`를
  그대로 재사용하지 않고 게임 전용 CSS를 별도로 둔다 (단, 라이트/다크 모드 대응과
  "장식보다 콘텐츠 우선"이라는 프로젝트 디자인 원칙은 동일하게 따른다)

## 2. 저장소 구조 파악 결과 (참고용, 이번 단계에서 수정 없음)

- `src/build.js`: `dist/`를 **완전히 삭제 후 재생성**한다 (`rmSync(DIST_DIR, {recursive:true, force:true})`).
  `posts/*.md`를 읽어 `dist/index.html`, `dist/posts/*.html`을 생성하고,
  `src/styles.css`, `src/site.js`만 `dist/`로 복사한다. **`/apps/`를 건드리는 코드는 현재 없음.**
- `src/templates.js`: `layout()`(공통 HTML 뼈대 + 헤더/푸터/다크모드 토글),
  `indexPage(posts)`(글 목록), `postPage(post)`(개별 글)를 export하는 순수 문자열 템플릿 함수.
- `scripts/serve.js`(`npm run dev`): 빌드를 한 번 실행한 뒤 **`dist/` 디렉터리만** 정적으로 서빙한다.
  즉 `dist/`에 없는 파일은 로컬 개발 서버에서도 절대 보이지 않는다.
- `.github/workflows/deploy.yml`: `npm run build` 실행 후 **`dist/` 폴더만** GitHub Pages 아티팩트로
  업로드한다. 즉 `/apps/2048/`이 `dist/`로 복사되지 않으면 배포 결과물에도 포함되지 않는다.

**결론**: `/apps/2048/`의 정적 파일들은 `dist/apps/2048/`로 복사되어야 로컬 개발 서버와 실제
배포(GitHub Pages) 양쪽에서 접근 가능하다. 이 복사 로직을 `src/build.js`에 추가하는 것이
Embed 단계의 핵심 작업이다 (자세한 내용은 8절 참고).

## 3. 파일 구조

```
apps/2048/
├── spec.md        # (본 문서, plan 단계 산출물)
├── index.html      # 게임 페이지 마크업 (점수판, 그리드, 오버레이)
├── style.css       # 게임 전용 스타일 (라이트/다크, 반응형)
└── game.js         # 게임 로직 + 렌더링 + 입력 처리
```

- 외부 라이브러리: **불필요**. 그리드 연산, 랜덤 타일 생성, 키보드/터치 입력 모두
  순수 JS로 충분히 구현 가능한 범위이므로 CDN 라이브러리를 도입하지 않는다.
- 이미지/폰트 등 별도 에셋 없음 (타일 색상은 CSS로 표현).

## 4. 각 파일의 역할

### `index.html`
- `<meta viewport>`, 타이틀(`2048`), `style.css` 링크
- 블로그 메인으로 돌아가는 링크(예: "← 블로그로")
- 헤더: 게임 제목 + 점수판(현재 점수 `#score`, 최고 점수 `#best-score`) + 새 게임 버튼(`#restart`)
- 게임 보드 컨테이너(`#board`, 4x4 그리드 — 배경 셀 16개 + 타일을 동적으로 그 위에 렌더링)
- 게임 종료/승리 시 보여줄 오버레이(`#game-message`, 기본 숨김) — "게임 오버" 또는
  "2048 달성! 계속하기 / 새 게임" 버튼 포함
- 모바일 대응 안내 텍스트 (예: "화살표 키 또는 스와이프로 이동")
- `<script src="game.js" defer></script>`

### `style.css`
- 블로그와 동일한 방식(라이트 기본값 + `prefers-color-scheme: dark` + `data-theme` 속성 오버라이드)의
  CSS 변수 기반 다크모드. 단, 블로그의 `styles.css`를 import/재사용하지 않고 이 앱에 필요한
  최소 변수만 자체 정의(배경, 텍스트, 보드 배경, 타일별 색상 등)
- 보드: CSS Grid `4x4`, `aspect-ratio: 1`로 정사각형 유지, `max-width`로 데스크톱에서 과도하게
  커지지 않게 제한
- 타일 색상: 값(2,4,8,16,...,2048)별로 클래스(`.tile-2`, `.tile-4`, ...) 또는 `data-value` 속성
  선택자로 배경색 매핑. 색상 팔레트는 라이트/다크 각각 대비가 충분하도록 CSS 변수로 관리
- 반응형: 모바일 뷰포트에서 보드가 화면 너비에 맞게 축소되도록 유동적 크기(`vw` 또는 `%` 기반)
- 애니메이션: 블로그 원칙("불필요한 장식/애니메이션 지양")을 존중하되, 타일 등장/병합 시
  최소한의 시각적 피드백(예: 짧은 `transform: scale` 트랜지션 정도)만 두는 것을 제안 —
  타일 이동 자체를 매끄럽게 슬라이딩시키는 좌표 애니메이션까지는 굳이 구현하지 않고
  "이동 후 즉시 재렌더링" 방식으로 단순화 (과설계 방지)

### `game.js`
- 게임 상태, 로직, DOM 렌더링, 입력 처리를 모두 포함 (규모가 작으므로 파일 분리는 하지 않음)

## 5. 게임 로직 핵심 설계

### 자료구조
- `board`: `number[4][4]` — 0은 빈 칸, 그 외는 타일 값(2, 4, 8, ...)
- `score`: `number` — 현재 게임의 누적 점수 (타일이 병합될 때마다 병합된 값만큼 증가)
- `bestScore`: `number` — `localStorage.getItem("2048-best-score")`에서 로드, 게임 중 갱신 시 저장
- `won`: `boolean` — 2048 타일을 처음 만든 시점 이후 "계속하기"를 눌렀는지 여부 (승리 후에도
  계속 플레이할 수 있게 하기 위한 플래그)

### 주요 함수
- `createEmptyBoard()`: `4x4` 0으로 채워진 배열 생성
- `addRandomTile(board)`: 빈 칸(`0`) 목록 중 무작위 위치 하나에 90% 확률로 2, 10% 확률로 4 배치
- `slideAndMergeLine(line)`: 길이 4인 1차원 배열 하나를 "왼쪽으로 밀기" 기준으로 압축 + 병합
  (0 제거 → 인접한 동일 값 병합(1회만) → 병합으로 생긴 점수 반환 → 다시 0으로 채워 길이 4 유지)
- `move(direction)`: `direction`(`"up"|"down"|"left"|"right"`)에 따라
  1) 보드를 회전/전치하여 "왼쪽 이동" 케이스로 정규화
  2) 각 행에 `slideAndMergeLine` 적용
  3) 다시 원래 방향으로 역회전
  4) 이동 전/후 보드를 비교해 변화가 있었는지(`moved`) 판별
  → 이렇게 4방향 로직을 하나의 핵심 함수로 재사용해 중복을 줄임
- `boardsEqual(a, b)`: 이동으로 실제 변화가 있었는지 비교 (변화 없으면 새 타일을 추가하지 않음 —
  2048 규칙상 유효하지 않은 이동은 턴을 소모하지 않아야 함)
- `isGameOver(board)`: 빈 칸이 없고, 상하좌우 인접 칸 중 병합 가능한 쌍이 하나도 없으면 true
- `hasWon(board)`: 보드 내 어떤 타일이든 값이 2048 이상이면 true
- `restart()`: 보드 초기화, 점수 0, 타일 2개 랜덤 배치, 메시지 오버레이 숨김
- `render()`: 현재 `board`/`score`/`bestScore` 상태를 DOM에 반영 (타일 엘리먼트 재생성 또는
  기존 16칸 갱신)

### 진행 흐름
1. 페이지 로드 시 `restart()`로 초기 보드(타일 2개) 생성 + `bestScore` localStorage에서 로드
2. 입력 발생 → `move(direction)` 호출 → `moved`가 true면 `addRandomTile` + 점수 갱신 +
   `bestScore` 갱신(필요 시 localStorage 저장) → `render()`
3. 매 이동 후 `hasWon`이면(아직 승리 처리 전이라면) 승리 오버레이 표시, "계속하기" 선택 시 게임 유지
4. 매 이동 후 `isGameOver`이면 게임 오버 오버레이 표시 + 새 게임 버튼 강조

## 6. UI/UX 및 조작 방식

- **키보드**: `keydown` 이벤트에서 `ArrowUp/Down/Left/Right` 캡처, `event.preventDefault()`로
  페이지 스크롤 방지 후 `move()` 호출
- **모바일 터치 스와이프**: `#board`에 `touchstart`/`touchend` 리스너 등록,
  시작/끝 좌표 차이(`dx`, `dy`)를 계산해 절댓값이 더 큰 축과 최소 스와이프 거리(threshold,
  예: 20~30px)를 기준으로 방향 판정 → 같은 `move()` 호출로 연결 (키보드/터치 로직을 공유)
- **점수판**: 상단에 "SCORE"(현재), "BEST"(최고) 두 박스. 최고 점수는 갱신될 때만 저장/표시 업데이트
- **새 게임 버튼**: 언제든 클릭하면 `restart()` (확인 다이얼로그 등 과설계 없이 즉시 초기화)
- **게임 종료/승리 오버레이**: 보드 위에 반투명 레이어 + 메시지 + 버튼. 최소한의 UI로 처리
  (별도 모달 라이브러리 불필요)
- **다크모드**: 블로그 본체처럼 시스템 설정 자동 감지. 수동 토글까지는 이 앱에서 필수는 아니라고
  제안 — 게임 자체가 짧은 세션 사용이 많아 토글 버튼까지 넣는 것은 과설계 소지 있음
  (필요하면 Embed 단계에서 사용자와 논의 후 추가)
- **접근성/여백**: 블로그 디자인 원칙(여백, 가독성)에 맞춰 헤더/설명 텍스트는 담백하게,
  게임 보드가 화면 중앙에 오도록 배치

## 7. localStorage 사용 범위 (제안, 과설계 방지)

- 저장 키 1개만 사용: `2048-best-score` (숫자 문자열)
- 그 외 게임 진행 상태(진행 중인 보드 등) 저장/복원 기능은 요구사항에 없으므로 구현하지 않음
  (새로고침하면 새 게임 시작)

## 8. Embed 단계 메모 — 블로그 메인 페이지에서 수정이 필요한 지점

1. **`src/build.js`**
   - `dist/`를 지우고 재생성하는 현재 로직 특성상, `/apps/` 디렉터리를 `dist/apps/`로
     복사하는 단계를 빌드 과정에 추가해야 배포/로컬 서버 양쪽에서 게임이 보인다.
   - 구현 방식은 두 가지 정도를 고려할 수 있음 (Embed 단계에서 택일):
     a) `apps/2048/`만 특정해서 복사
     b) `/apps/` 하위 전체를 재귀 복사하는 범용 로직을 추가해 향후 다른 미니 웹앱이 추가되어도
        `build.js`를 다시 건드리지 않아도 되게 함 (기존 `copyFileSync` 패턴에 맞춰 작은
        재귀 복사 헬퍼 함수 하나 추가하는 정도로 충분, 별도 라이브러리 불필요)
   - `rmSync(DIST_DIR, ...)` 이후, `mkdirSync`/copy 순서를 기존 posts 복사 로직과 나란히 배치

2. **`src/templates.js`**
   - `indexPage(posts)`(또는 `layout()`의 헤더)에 게임 앱으로 연결되는 링크를 추가해야 발견 가능해짐.
     예: 글 목록 위/아래에 "미니 웹앱" 섹션을 하나 추가하고 `apps/2048/index.html`로 가는
     링크(및 짧은 설명 "방향키로 즐기는 2048 게임")를 넣는 정도로 최소화해서 제안.
   - `apps/2048/index.html`은 블로그의 `layout()` 템플릿을 쓰지 않는 완전 별도 HTML이므로,
     `templates.js` 쪽에서는 "링크 추가"만 필요하고 `layout()` 자체의 구조 변경은 불필요.

3. **`src/styles.css`**
   - 변경 불필요 (게임은 자체 `style.css`를 사용하는 self-contained 앱). 다만 블로그 인덱스에
     추가되는 "미니 웹앱 링크" 항목의 스타일(예: `.post-item`과 비슷한 리스트 스타일 재사용 또는
     소규모 클래스 하나 추가) 정도는 Embed 단계에서 필요할 수 있음 — 새 컴포넌트 급의 CSS는
     아니므로 기존 `.post-item` 스타일을 그대로 재사용하는 방향을 우선 검토.

4. **배포 워크플로(`.github/workflows/deploy.yml`)**
   - 별도 수정 불필요. `npm run build`가 `dist/`에 `apps/`까지 포함하도록만 고치면
     기존 `upload-pages-artifact` 단계가 `dist/` 전체를 그대로 업로드하므로 자동으로 함께 배포됨.

## 9. 범위 밖 (이번 계획에 포함하지 않음)

- 리더보드 서버, 계정/로그인, 다른 사람과 점수 비교 등 서버가 필요한 기능
- 실행 취소(undo), 이동 애니메이션 고도화, 사운드 효과
- 진행 중 보드 저장/복원 (새로고침 시 이어하기)

이상으로 계획 수립을 마친다. 실제 구현(HTML/CSS/JS 작성, `build.js`/`templates.js` 수정)은
Embed 단계에서 진행한다.
