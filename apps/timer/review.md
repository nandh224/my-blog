# 타이머/스톱워치 - Review 결과

> 이 문서는 Review 단계 산출물이다. Build 서브에이전트와 독립적으로 `index.html`,
> `style.css`, `timer.js`를 `spec.md`와 대조하며 검증했다.

## 1. 검증 방법

이 환경에서는 브라우저 자동화 도구(Playwright/Puppeteer 등)를 사용할 수 없었다
(`package.json`에 관련 의존성 없음, 브라우저 자동화 툴 미탑재). 따라서 지침의
대안 절차에 따라 다음 두 가지 방식으로 검증했다.

1. **정적 코드 검토**: `spec.md`의 자료구조/함수 설계/모드 전환 정책/타이밍 정확도
   원칙과 `index.html`, `style.css`, `timer.js` 실제 구현을 한 줄 단위로 대조.
2. **순수 로직 발췌 테스트(Node.js)**: `timer.js`에서 DOM에 의존하지 않는 함수
   (`pad`, `formatCountdown`, `formatStopwatch`)를 그대로 발췌하고, `Date.now()`
   기반 재계산 로직(카운트다운 잔여시간 계산식, 스톱워치 경과시간 계산식, pause/resume
   누적식, `finished` 플래그를 이용한 중복 알림 방지, reset 후 재시작 분기)을
   동일한 수식으로 재현해 검증 스크립트를 작성·실행했다. 이 스크립트는 검증용 임시
   산출물이므로 저장소 밖 스크래치패드
   (`.../scratchpad/timer-logic-test.mjs`)에 작성했고 `/apps/timer/` 안에는 남기지
   않았다.
   - 총 18개 assertion, 전부 통과(PASS). 확인한 내용:
     - `formatCountdown`/`formatStopwatch`의 분/초/10분의1초 포맷팅 (0, 자릿수 올림,
       60초 이월, 60분 이상 표기 등 경계값)
     - `setInterval` 트리거 간격이 90~150ms로 불규칙(들쭉날쭉)하게 들어와도, 매 틱마다
       `Date.now()` 기반으로 남은/경과 시간을 다시 계산하는 방식이므로 실제 경과시간과
       정확히 일치함 (틱 횟수 기반 계산이었다면 발생했을 누적 오차가 없음을 확인)
     - 스톱워치를 3번 연속 일시정지/재개해도 `elapsedMs` 누적이 정확함(3s → 5s → 6.5s)
     - 카운트다운이 여러 틱에 걸쳐 계속 0 이하를 반환해도 `finished` 플래그 덕분에
       완료 콜백(비프음 트리거)이 정확히 1회만 실행됨
     - `finished` 상태에서는 리셋 없이 재시작되지 않고, 리셋 후에는 입력값 기준으로
       정상적으로 재시작됨
3. **경로/일관성 확인**: 블로그 복귀 링크(`../../index.html`)가 실제 저장소 루트의
   `index.html`을 정확히 가리키는지, 그리고 `apps/2048/index.html`의 동일 패턴과
   비교해 확인. 또한 `apps/timer/style.css`의 라이트/다크 CSS 변수 값이
   `src/styles.css`의 값과 정확히 일치하는지 `grep`으로 대조 확인(모두 일치).

브라우저에서 직접 클릭/탭하며 확인하는 절차는 수행하지 못했으므로, 위 정적/로직
검증으로 커버되지 않는 순수 렌더링/이벤트 배선(예: 버튼 클릭이 실제 DOM 이벤트로
정확히 연결되는지)은 코드 리딩으로 교차 확인했다(각 버튼에 `addEventListener`가
정확한 핸들러로 1:1 연결되어 있음을 확인).

## 2. 발견한 문제

### 문제 1 (경미) — 일시정지 중 입력값 편집 시 표시-상태 불일치 → **수정함**

`pauseCountdown()`이 `setCountdownInputsDisabled(false)`를 호출해 일시정지 중에도
분/초 입력 필드를 다시 활성화하고 있었다. 그런데 `handleCountdownInputChange()`는
"정지 상태(`!countdown.running`)"일 때 입력값을 읽어 `#cd-display` 미리보기만
갱신할 뿐, 실제 `countdown.remainingMs`/`totalMs`는 그대로 두는 구조였다.

재현 시나리오: 10분 카운트다운을 시작 → 일시정지(예: 8분 남음) → 입력 필드를
2분으로 수정하면 화면에는 "02:00"이 미리보기로 표시되지만, 내부 `remainingMs`는
여전히 8분(480000ms)으로 남아 있음 → 다시 "시작"을 누르면 화면이 곧바로 "08:00"
근처 값으로 되돌아가며 사용자가 입력한 2분이 조용히 무시됨. 사용자 입장에서는
"방금 바꾼 값이 반영되지 않고 사라졌다"는 버그로 인지될 수 있는 표시-상태 불일치다.

**수정 내용**: `pauseCountdown()`에서 `setCountdownInputsDisabled(false)` 호출을
제거했다(`apps/timer/timer.js`). 이제 입력 필드는 `remainingMs`가 실제로 0이 되는
시점(`resetCountdown()`, `onCountdownFinished()`)에만 다시 활성화되며, 진행 중인
카운트다운 세션이 남아 있는 동안(실행 중이든 일시정지든)은 계속 비활성 상태를
유지해 표시값과 내부 상태가 항상 일치하도록 했다. `spec.md`의 "실행 중에는
disabled"라는 문구를 문자 그대로는 넘어서지만, spec이 명시한 pause/resume 상태
보존 원칙("일시정지 시 상태값 보존")과 실제 UI가 보여주는 값이 어긋나지 않아야
한다는 더 근본적인 요구를 지키기 위한 최소 수정이라 판단했다.

### 문제 2 (경미, 접근성) — 매 100ms 갱신되는 시간 표시에 `aria-live="polite"` → **수정함**

`spec.md` 6절은 "시간 표시 영역은 `aria-live="polite"` 정도를 검토해 스크린 리더가
**과도하게 자주 읽지 않으면서도** 상태 변화(완료 등)는 알 수 있게" 하라고 명시했다.
그런데 실제 구현은 `aria-live="polite"`를 계속 갱신되는 `#cd-display`,
`#sw-display`(100ms 간격으로 `textContent`가 바뀜) 자체에 걸어두고 있었다. `polite`는
발화를 끊지는 않지만 값이 바뀔 때마다 알림 큐에 쌓이므로, 카운트다운/스톱워치가
동작하는 내내 스크린 리더가 초 단위로 계속 시간을 읽어주게 되어 spec이 우려한
"과도하게 자주 읽는" 상황을 오히려 만드는 구현이었다.

**수정 내용**: `#cd-display`, `#sw-display`에서 `aria-live="polite"`를 제거하고,
평소 숨겨져 있다가 완료 시 1회만 노출되는 `#cd-status`("시간 종료!")에
`aria-live="polite"`를 옮겼다(`apps/timer/index.html`). 이렇게 하면 매 tick의
소음 없이 "완료"라는 상태 변화만 스크린 리더에 전달되어 spec의 의도에 더 부합한다.

## 3. 남아있는(수정하지 않은) 이슈 — 제안 수준

- **탭 접근성 마크업 미완성**: `.tabs`에 `role="tablist"`, 각 버튼에 `role="tab"`/
  `aria-selected`는 있으나, `role="tabpanel"`이나 `aria-controls`로 탭-패널을
  명시적으로 연결하지는 않았다. `spec.md` 6절이 접근성을 "필수 요구사항은 아니므로
  시간이 부족하면 생략 가능"이라고 명시했으므로 구조적 재작업(탭/패널 id 상호
  참조, 포커스 관리 등) 없이 그대로 두었다. 필요시 후속 작업으로 남긴다.
- **완료 직후 입력값 편집 시 시각적 잔상**: 카운트다운 완료 후(`finished=true`)에는
  입력 필드가 다시 활성화되는데, 이 상태에서 사용자가 분/초를 바꾸면 `#cd-display`
  미리보기는 갱신되지만 "시간 종료!" 문구와 `.finished`(경고색) 스타일은 리셋을
  누르기 전까지 그대로 남아 있다. 사용법 안내 문구가 "카운트다운이 끝난 뒤 다시
  시작하려면 먼저 리셋을 눌러주세요"라고 명시하고 있어 기능적으로는 문제가 없고
  기능 결함이라기보다 사소한 시각적 잔상이라 판단해 손대지 않았다. 재작업 시
  입력값 변경을 감지해 `.finished` 클래스/상태 문구를 함께 지우는 것을 고려할 수
  있다.
- 브라우저 실제 클릭/탭 동작, 콘솔 에러 유무는 자동화 도구 부재로 직접 확인하지
  못했다(1절 참고). 코드 리딩상 이벤트 배선과 상태 전이 로직에는 문제를 발견하지
  못했다.

## 4. 확인했으나 문제 없었던 항목

- `[hidden]` 속성과 `.panel { display:flex }`의 캐스케이드 충돌: Build 단계에서
  이미 `.panel[hidden] { display: none; }` 규칙과 명시적 주석으로 선제 대응되어
  있음을 확인(2048 앱에서 실제 발생했던 버그 패턴과 동일한 원인이지만 여기서는
  이미 해결됨).
- 라이트/다크 모드 CSS 변수: `src/styles.css`의 값과 `apps/timer/style.css`의
  라이트/다크 값이 `--bg`/`--text`/`--text-secondary`/`--link`/`--border`/
  `--code-bg` 전부 정확히 일치함을 확인(`grep`으로 대조).
- 블로그 복귀 링크(`../../index.html`)가 저장소 루트 `index.html`을 정확히
  가리키며, `apps/2048/index.html`의 동일 링크 패턴과 일치함을 확인.
- 모바일 대응: `inputmode="numeric"`, 버튼/입력 최소 44px 탭 영역, `flex-wrap`
  기반 반응형 레이아웃 확인. 드래그/스와이프 같은 커스텀 터치 제스처가 없는 앱이라
  (버튼·숫자 입력만 사용) 별도의 터치 스크롤 방지 처리는 필요하지 않다고 판단.
  타이밍 정확도 원칙(`Date.now()` 기반 재계산, `setInterval(tick, 100)`),
  `finished` 플래그를 통한 중복 알림 방지, 모드 전환 시 자동 일시정지(상태 보존)
  로직은 모두 `spec.md` 설계와 일치함(1절의 로직 테스트로 교차 검증).

## 5. 최종 결론

`spec.md`에서 정의한 카운트다운/스톱워치 핵심 로직(타이밍 정확도, 모드 전환 정책,
완료 판정과 중복 알림 방지, 리셋/재시작)은 설계대로 정확히 구현되어 있음을 코드
검토와 순수 로직 테스트로 확인했다. 검토 중 발견한 두 가지 경미한 문제(일시정지 중
입력 편집 시 상태 불일치, 시간 표시의 `aria-live` 과다 알림)는 범위 내에서 직접
수정했다. 남은 이슈는 모두 spec이 명시적으로 선택적(optional)이라고 밝힌 접근성
향상 항목이거나 기능에 영향이 없는 사소한 시각적 잔상이다. 브라우저 수동
클릭/키보드 테스트까지는 이 환경에서 수행하지 못했다는 제약이 있지만, 정적 검토와
로직 테스트 범위 내에서는 **이 앱이 정상 동작한다고 판단한다.**
